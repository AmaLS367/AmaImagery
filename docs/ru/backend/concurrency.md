# Async ORM и модель конкурентности

## Обзор

Бэкенд использует **async SQLAlchemy** для всех операций с базой данных, чтобы обеспечить неблокирующий I/O и оптимальное использование event loop. Тяжелые операции делегируются фоновым воркерам для поддержания отзывчивости HTTP обработчиков.

## Async ORM

### Операции с базой данных

Все операции с базой данных используют async SQLAlchemy:

- **Async Engine** - `create_async_engine()` с async драйверами (asyncpg для PostgreSQL, aiosqlite для SQLite)
- **Async Session** - `AsyncSession` для всех взаимодействий с БД
- **Async Repositories** - Все методы репозиториев `async def`
- **Async UnitOfWork** - Управление транзакциями через async context managers

### Пример

```python
from app.infra.uow import get_uow

# Все операции с БД асинхронные
uow = get_uow()
async with uow:
    user = await uow.users.get(user_id)
    generations = await uow.generations.list_by_user(user_id)
    # Транзакция автоматически коммитится
```

### Правила

- ✅ **Все операции с БД ДОЛЖНЫ быть async**
- ✅ **Используйте `await` для всех методов репозиториев**
- ✅ **Используйте `AsyncSession` во всех handlers и сервисах**
- ❌ **НЕ используйте sync `Session` в async коде**
- ❌ **НЕ используйте `asyncio.to_thread` для операций с БД** (используйте async API)

## Модель конкурентности

### Архитектурные слои

```
HTTP Handler (FastAPI) → Use Case → UnitOfWork → Repository → Async DB
                                    ↓
                              TaskQueue (Redis)
                                    ↓
                              Worker Process
                                    ↓
                          Тяжелые операции (ML и т.д.)
```

### Поток запросов

1. **HTTP Handler** - FastAPI endpoint получает запрос
   - **Только легкие операции**: валидация, аутентификация, парсинг запроса
   - **Нет блокирующих операций**: нет тяжелых вычислений, нет долгих задач
   - **Быстрый ответ**: возвращает сразу или ставит задачу в очередь

2. **Use Case** - Оркестрация бизнес-логики
   - Координирует работу репозиториев, провайдеров и очередей
   - Валидирует бизнес-правила
   - Ставит тяжелые задачи в очередь при необходимости

3. **UnitOfWork** - Управление транзакциями
   - Управляет async транзакциями БД
   - Координирует несколько репозиториев

4. **Repository** - Доступ к данным
   - Async запросы к БД
   - Неблокирующие I/O операции

5. **TaskQueue** - Асинхронная обработка задач
   - Тяжелые операции ставятся в очередь
   - Redis используется только как транспортная очередь

6. **Worker Process** - Фоновая обработка
   - Берет задачи из очереди
   - Выполняет тяжелые операции (ML inference, обработка изображений)
   - Обновляет lifecycle-состояние в PostgreSQL

## Тяжелые операции

### Что идет в воркеры

Следующие операции **ДОЛЖНЫ** выполняться в фоновых воркерах:

- **ML Inference** - Генерация изображений и provider-side обработка, которая занимает заметное время
- **Обработка изображений** - Конвертация форматов и подготовка артефактов, когда такие операции входят в worker flow
- **Операции с файлами** - Загрузка/скачивание больших файлов, пакетная обработка
- **Вызовы внешних API** - Долгие вызовы внешних сервисов
- **Обработка данных** - Обработка больших наборов данных, пакетные операции

### Что остается в handlers

Следующие операции **допустимы** в HTTP handlers:

- **Валидация** - Проверка входных данных, бизнес-правила
- **Аутентификация** - Проверка токенов, поиск пользователя
- **Легкие запросы** - Простые запросы к БД (информация о пользователе, настройки)
- **Проверка статуса** - Получение статуса задачи из DB-backed lifecycle
- **Форматирование ответа** - Трансформация данных для API ответов

## Правила и лучшие практики

### ✅ Можно

- **Держать handlers легкими** - Возвращать быстро, ставить тяжелую работу в очередь
- **Использовать async для всех операций с БД** - Никогда не блокировать event loop
- **Делегировать тяжелые операции** - Использовать TaskQueue и воркеры
- **Отслеживать статус задач** - Использовать endpoints статуса для долгих операций
- **Обрабатывать ошибки корректно** - Возвращать соответствующие HTTP статус коды

### ❌ Нельзя

- **НЕ выполнять тяжелые операции в handlers** - Нет ML inference, нет долгих операций с файлами
- **НЕ использовать sync вызовы к БД** - Всегда использовать async API
- **НЕ блокировать event loop** - Нет CPU-интенсивной работы в handlers
- **НЕ ждать результатов воркеров** - Использовать async модель задач с опросом статуса
- **НЕ смешивать sync и async** - Держать async код консистентным

## Очередь и воркеры

### Очередь задач

- **Назначение**: Разделить HTTP запросы и тяжелую обработку
- **Реализация**: Очередь на основе Redis с хранением lifecycle в базе данных
- **Жизненный цикл задачи**: `queued` → `running` → `completed`/`failed`

### Воркеры

- **Назначение**: Обрабатывать тяжелые задачи асинхронно
- **Развертывание**: Отдельные процессы/контейнеры
- **Масштабирование**: Можно запускать несколько экземпляров воркеров

### Пример потока

```python
# Handler: Быстрый ответ
@router.post("/api/v1/images/generate")
async def generate(request: GenReq):
    use_case = GenerateImageUseCase(uow=get_uow())
    result = await use_case(GenerateImageCommand(...))
    return TaskResp(task_id=result.data.task_id, status="queued")

# Worker: Тяжелая обработка
async def run_worker():
    while True:
        generation_id = await task_queue.dequeue()
        # Тяжелый ML inference здесь
        generation = await uow.generations.get(generation_id)
        submission = await provider.submit(...)
        result = await provider.wait_for_result(submission, timeout_sec=...)
        await uow.generations.update_fields(generation_id, status="completed", result=result.metadata)
```

## Безопасность Event Loop

### Неблокирующие операции

Все I/O операции неблокирующие:

- **База данных**: Async SQLAlchemy с asyncpg/aiosqlite
- **Redis**: Async Redis клиент
- **HTTP**: Async httpx для внешних вызовов
- **File I/O**: Async операции с файлами где возможно

### Блокирующие операции

Некоторые операции по своей природе блокирующие и должны обрабатываться осторожно:

- **ML Inference**: Операции PyTorch (обернуты в `asyncio.to_thread` в провайдерах)
- **CPU-интенсивные задачи**: Делегируются воркерам
- **Синхронные библиотеки**: Оборачиваются или заменяются async альтернативами

## Соображения производительности

### Производительность Handlers

- **Цель**: < 100ms время ответа для handlers
- **Запросы к БД**: Оптимизированы с индексами, пулом соединений
- **Кэширование**: Redis для часто используемых данных
- **Пул соединений**: Async engine с пулом соединений

### Производительность Воркеров

- **Пропускная способность**: Обрабатывать несколько задач параллельно
- **Управление ресурсами**: Память GPU, CPU ядра
- **Обработка ошибок**: Логика повторов, отслеживание неудач
- **Мониторинг**: Длительность задач, частота успеха/неудачи

## Заметки по миграции

При миграции с sync на async:

1. Заменить `Session` на `AsyncSession`
2. Заменить `session.query()` на `select()` + `await session.execute()`
3. Заменить `session.get()` на `await session.get()`
4. Удалить обертки `asyncio.to_thread` для операций с БД
5. Обновить все методы репозиториев на `async def`
6. Обновить тестовые фикстуры для использования async сессий

## Тестирование Async кода

### Тестовые фикстуры

Используйте async фикстуры для тестов БД:

```python
@pytest_asyncio.fixture
async def uow():
    uow = get_uow()
    async with uow:
        yield uow
        await uow._session.rollback()
```

### Async тестовые функции

Помечайте async тестовые функции соответствующим образом:

```python
@pytest.mark.asyncio
async def test_user_repository(uow):
    user = await uow.users.get(user_id)
    assert user is not None
```
