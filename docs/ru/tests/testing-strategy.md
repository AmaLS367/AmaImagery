# Стратегия тестирования

## Обзор

Этот документ описывает стратегию тестирования для backend, включая уровни тестов, цели по покрытию и правила написания и запуска тестов.

## Уровни тестов

### Unit тесты

**Расположение:** `tests/unit/`

**Назначение:** Тестирование отдельных компонентов в изоляции с замоканными зависимостями.

**Характеристики:**
- Быстрое выполнение (без внешних зависимостей)
- Моки внешних сервисов (база данных, Redis, HTTP клиенты)
- Тестирование бизнес-логики, утилит и доменных моделей
- Должны быть детерминированными и повторяемыми

**Когда писать:**
- Тестирование чистых функций и утилит
- Тестирование доменной логики и бизнес-правил
- Тестирование методов сервисов с замоканными зависимостями
- Тестирование валидации и трансформации данных

**Примеры:**
- `test_safety_blocklist.py` - Логика фильтрации контента
- `test_settings_failfast.py` - Валидация конфигурации
- `test_utils_prompt_hash.py` - Утилитарные функции

### Интеграционные тесты

**Расположение:** `tests/integration/` и `tests/infra/`

**Назначение:** Тестирование компонентов, работающих вместе с реальными зависимостями (база данных, Redis и т.д.).

**Характеристики:**
- Использование реальной базы данных (in-memory SQLite или тестовый PostgreSQL)
- Использование реального Redis или замоканного клиента
- Тестирование реализаций репозиториев
- Тестирование API endpoints с test client
- Медленнее unit тестов, но более реалистичны

**Когда писать:**
- Тестирование реализаций репозиториев с реальной базой данных
- Тестирование API endpoints end-to-end
- Тестирование интеграции сервисов с внешними системами
- Тестирование миграций базы данных

**Примеры:**
- `test_auth_flow.py` - Поток аутентификации через API
- `test_db_migrations_alembic.py` - Миграции базы данных
- `test_rate_limit_redis.py` - Rate limiting на основе Redis
- `tests/infra/repositories/` - Интеграционные тесты репозиториев

### Тесты слоя приложения

**Расположение:** `tests/application/`

**Назначение:** Тестирование use cases и логики оркестрации приложения.

**Характеристики:**
- Тестирование классов use case с замоканными зависимостями
- Проверка бизнес-процессов и обработки ошибок
- Тестирование паттернов command/result
- Быстрое выполнение с замоканной инфраструктурой

**Примеры:**
- `test_generate_image_use_case.py` - Use case генерации изображений

### E2E тесты

**Расположение:** `tests/e2e/`

**Назначение:** Тестирование полных пользовательских сценариев через API.

**Характеристики:**
- Использование реального application server (должен быть запущен)
- Тестирование полных циклов request/response
- Проверка end-to-end функциональности
- Могут требовать внешние сервисы (база данных, Redis)

**Когда писать:**
- Тестирование критических пользовательских сценариев
- Тестирование API контрактов
- Smoke тесты для проверки деплоя

**Примеры:**
- `test_health_and_generate.py` - Health check и поток генерации
- `test_file_access_signed_url.py` - Доступ к файлам с подписанными URL

## Цели по покрытию

### Минимальный порог покрытия

**Цель: 80%** для пакета `app/`.

CI pipeline будет падать, если покрытие опустится ниже 80%. Это обеспечивает:
- Тестирование критической бизнес-логики
- Новые функции включают тесты
- Рефакторинг безопаснее с покрытием тестами

### Конфигурация покрытия

Покрытие настроено в `pyproject.toml`:

```toml
[tool.pytest.ini_options]
addopts = [
    "--cov=app",
    "--cov-report=term-missing",
    "--cov-report=html",
    "--cov-report=xml",
    "--cov-fail-under=80",
]

[tool.coverage.report]
fail_under = 80
```

### Исключения из покрытия

Следующее исключено из расчета покрытия:
- Файлы тестов (`tests/`)
- Файлы миграций (`migrations/`)
- Кэш директории (`__pycache__/`)
- Определения протоколов и абстрактные методы
- Блоки проверки типов (`if TYPE_CHECKING:`)

## Организация тестов

### Структура директорий

```
tests/
├── unit/              # Unit тесты (замоканные зависимости)
├── integration/       # Интеграционные тесты (реальные зависимости)
├── application/       # Тесты use cases
├── infra/            # Тесты инфраструктуры (репозитории, очередь, провайдеры)
│   ├── repositories/ # Интеграционные тесты репозиториев
│   ├── queue/        # Тесты очереди задач
│   └── providers/    # Тесты провайдеров
├── workers/          # Тесты воркеров
├── e2e/              # End-to-end тесты
├── security/         # Тесты безопасности
└── perf/             # Тесты производительности
```

### Соглашения по именованию

- Файлы тестов: `test_*.py`
- Функции тестов: `test_*`
- Классы тестов: `Test*`
- Фикстуры: `*_fixture` или описательные имена

## Написание тестов

### Правила для Unit тестов

1. **Мокируйте внешние зависимости:**
   ```python
   @patch('app.infra.queue.get_task_queue')
   async def test_use_case(mock_queue):
       # Реализация теста
   ```

2. **Используйте фикстуры для общей настройки:**
   ```python
   @pytest.fixture
   def mock_provider():
       provider = AsyncMock()
       provider.generate = AsyncMock(return_value=result)
       return provider
   ```

3. **Тестируйте одну вещь за раз:**
   - Одно утверждение или связанные утверждения
   - Понятное имя теста, описывающее что тестируется

4. **Следуйте паттерну AAA:**
   - Arrange: Настройка тестовых данных и моков
   - Act: Выполнение тестируемого кода
   - Assert: Проверка результатов

### Правила для интеграционных тестов

1. **Используйте тестовую базу данных:**
   - In-memory SQLite для тестов репозиториев
   - Тестовый PostgreSQL для полных интеграционных тестов

2. **Очищайте после тестов:**
   - Используйте фикстуры с автоматической очисткой
   - Откатывайте транзакции в тестах базы данных

3. **Используйте реальные зависимости когда возможно:**
   - Реальный Redis клиент (или замоканный, но реалистичный)
   - Реальные подключения к базе данных
   - Реальные HTTP клиенты для внешних API

### Тестовые фикстуры

Общие фикстуры определены в `tests/conftest.py`:

- `app_client` - FastAPI test client
- `async_session` - Async сессия базы данных
- `async_db_engine` - Async движок базы данных
- `uow` - UnitOfWork с автоматическим откатом
- `test_db_session` - Тестовая сессия базы данных для репозиториев

## Запуск тестов

### Локальная разработка

**Запустить все тесты:**
```bash
pytest tests/
```

**Запустить с покрытием:**
```bash
pytest tests/ --cov=app --cov-report=term-missing
```

**Запустить конкретный уровень тестов:**
```bash
# Только unit тесты
pytest tests/unit/

# Только интеграционные тесты
pytest tests/integration/

# Тесты слоя приложения
pytest tests/application/
```

**Запустить конкретный файл тестов:**
```bash
pytest tests/application/test_generate_image_use_case.py
```

**Запустить с маркерами:**
```bash
# Пропустить медленные тесты
pytest tests/ -m "not slow"

# Запустить только async тесты
pytest tests/ -m asyncio
```

### Настройка тестовой базы данных

**Для тестов репозиториев:**
- Использует in-memory SQLite (автоматически)
- Настройка не требуется

**Для интеграционных тестов:**
- Требует запущенный PostgreSQL
- Установите переменную окружения `DATABASE_URL`:
  ```bash
  export DATABASE_URL=postgresql+psycopg2://user:pass@localhost:5432/testdb
  ```

**Для E2E тестов:**
- Требует запущенный application server
- Запустите сервер: `python run.py`
- Запустите тесты в отдельном терминале

### CI/CD

Тесты запускаются автоматически в GitHub Actions при:
- Push в ветки `main` или `develop`
- Pull requests

**Конфигурация CI:**
- Контейнер сервиса PostgreSQL
- Контейнер сервиса Redis
- Порог покрытия: 80%
- Падает, если покрытие ниже порога

См. `.github/workflows/tests.yml` для деталей.

## Лучшие практики

### Когда писать Unit тесты

- ✅ Чистые функции и утилиты
- ✅ Доменная логика и бизнес-правила
- ✅ Методы сервисов с замоканными зависимостями
- ✅ Логика валидации и трансформации
- ❌ Не тестируйте код фреймворка (внутренности FastAPI, SQLAlchemy)
- ❌ Не тестируйте код сторонних библиотек

### Когда писать интеграционные тесты

- ✅ Реализации репозиториев
- ✅ API endpoints
- ✅ Интеграция сервисов с внешними системами
- ✅ Миграции базы данных
- ✅ Взаимодействие очереди и воркеров
- ❌ Не дублируйте покрытие unit тестов
- ❌ Не тестируйте внешние сервисы (используйте моки)

### Когда писать E2E тесты

- ✅ Критические пользовательские сценарии
- ✅ API контракты
- ✅ Smoke тесты для деплоя
- ❌ Не тестируйте каждый endpoint (используйте интеграционные тесты)
- ❌ Не тестируйте граничные случаи (используйте unit тесты)

### Правила качества тестов

1. **Тесты должны быть быстрыми:**
   - Unit тесты: < 1 секунды каждый
   - Интеграционные тесты: < 10 секунд каждый
   - E2E тесты: < 30 секунд каждый

2. **Тесты должны быть независимыми:**
   - Нет общего состояния между тестами
   - Каждый тест может запускаться изолированно
   - Тесты могут запускаться в любом порядке

3. **Тесты должны быть детерминированными:**
   - Одинаковый ввод всегда дает одинаковый вывод
   - Нет случайных данных (используйте фиксированные seeds)
   - Нет логики, зависящей от времени (мокируйте время)

4. **Тесты должны быть читаемыми:**
   - Понятные имена тестов
   - Минимальный код настройки
   - Очевидные утверждения

5. **Тесты должны быть поддерживаемыми:**
   - Используйте фикстуры для общей настройки
   - Извлекайте вспомогательные функции
   - Держите тесты DRY (но читаемыми)

## Решение проблем

### Тесты падают локально

1. **Проверьте переменные окружения:**
   ```bash
   export DATABASE_URL=postgresql+psycopg2://...
   export REDIS_URL=redis://localhost:6379/0
   export SECRET_KEY=test-secret-key
   ```

2. **Проверьте зависимости:**
   ```bash
   pip install -e .
   pip install pytest pytest-cov pytest-asyncio
   ```

3. **Проверьте базу данных:**
   - Убедитесь, что PostgreSQL запущен
   - База данных существует и доступна

4. **Проверьте Redis:**
   - Убедитесь, что Redis запущен
   - Строка подключения правильная

### Покрытие ниже порога

1. **Проверьте отчет о покрытии:**
   ```bash
   pytest tests/ --cov=app --cov-report=html
   # Откройте htmlcov/index.html
   ```

2. **Определите непокрытый код:**
   - Просмотрите HTML отчет
   - Добавьте тесты для непокрытых путей
   - Исключите нетestable код (протоколы, абстрактные методы)

3. **Временное исключение:**
   ```python
   # pragma: no cover
   def untestable_function():
       ...
   ```
